# San Mines — Master Technical Architecture & Knowledge Guide

This document is the comprehensive, canonical technical reference for the **San Mines Logistics & Dispatch Tracking Platform**. It covers system architecture, database DDL schemas, API request flows, security, mathematical algorithms, client state management, and implementation guidelines for human engineers and AI models (such as Claude AI).

---

## 1. System Overview & Domain Architecture

**San Mines** is an enterprise mining logistics management platform engineered to track heavy material haulage lorries from quarry extraction nodes to unloading destination sites.

```
┌──────────────────────────────────────────────────────────────────────────────────┐
│                             SAN MINES ECOSYSTEM                                  │
├─────────────────────────┬─────────────────────────┬──────────────────────────────┤
│ 1. Quarry Yard Queue    │ 2. Fleet In Transit     │ 3. Unloading & Closeout      │
│    (INSIDE_QUARRY)      │    (IN_TRANSIT)          │    (UNLOADED)                │
│                         │                         │                              │
│ • Check-In Lorry        │ • Dispatch Check-Out    │ • Inbound Fleet View         │
│ • Axle / Wheel Count    │ • Gross Weight Capture  │ • Destination GPS Validate   │
│ • Tare Weight Capture   │ • Net Weight Compute    │ • Unload Photo Proof         │
│ • Entry Photo Proof     │ • Geofence GPS Check    │ • Trip Completed Archive     │
└─────────────────────────┴─────────────────────────┴──────────────────────────────┘
```

## 2. Technical Stack Specifications

### **Client Tier (`SM-Client`)**
- **Framework**: Expo SDK 54 / React Native (TypeScript strict mode)
- **Safe Area Management**: `react-native-safe-area-context`
- **Iconography**: `lucide-react-native`
- **State & Context**: React Context API (`AuthContext.tsx`) with in-memory lookup caching and zero-GET mutation updaters
- **HTTP Client**: Native `fetch` with modular wrapper (`src/lib/api.ts`), JWT authorization header injection, and unified error handling

### **Backend Server Tier (`SM-Server`)**
- **Runtime Environment**: Node.js (TypeScript compiled with `tsc` to `dist/`)
- **Web Framework**: Express.js with modular routing (`tripsRouter`, `configRouter`, `router`)
- **Database Backend**: Supabase (PostgreSQL with Row Level Security)
- **Authentication**: Custom JWT authentication middleware (`requireAuth`) & Role-Based Access Control (`authorizeRole`)
- **Logging**: Winston logger writing structured JSON logs (`logs/app-YYYY-MM-DD.log`)

## 3. Database Schemas & DDL Specifications

The underlying Supabase PostgreSQL database consists of 5 core tables.

### **SQL DDL Table Definitions**

```sql
-- 1. PROFILES TABLE (User Roles & Accounts)
CREATE TABLE public.profiles (
    id UUID PRIMARY KEY REFERENCES auth.users(id) ON DELETE CASCADE,
    email TEXT UNIQUE NOT NULL,
    role TEXT NOT NULL CHECK (role IN ('SUPER_ADMIN', 'QUARRY_OPERATOR', 'UNLOAD_OPERATOR')),
    full_name TEXT NOT NULL,
    is_active BOOLEAN DEFAULT true NOT NULL,
    created_at TIMESTAMP WITH TIME ZONE DEFAULT timezone('utc'::text, now()) NOT NULL
);

-- 2. LOCATIONS TABLE (Quarry Yards & Destination Nodes)
CREATE TABLE public.locations (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    name TEXT NOT NULL,
    node_type TEXT NOT NULL CHECK (node_type IN ('QUARRY', 'UNLOAD_SITE')),
    latitude NUMERIC(10, 8) NOT NULL,
    longitude NUMERIC(11, 8) NOT NULL,
    allowed_radius_meters NUMERIC DEFAULT 100 NOT NULL,
    is_active BOOLEAN DEFAULT true NOT NULL,
    created_at TIMESTAMP WITH TIME ZONE DEFAULT timezone('utc'::text, now()) NOT NULL
);

-- 3. MATERIALS TABLE (Aggregate Material Chips)
CREATE TABLE public.materials (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    material_name TEXT UNIQUE NOT NULL,
    display_name TEXT NOT NULL,
    created_at TIMESTAMP WITH TIME ZONE DEFAULT timezone('utc'::text, now()) NOT NULL
);

-- 4. WHEEL_TYPES TABLE (Vehicle Lorry Axle Configurations)
CREATE TABLE public.wheel_types (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    wheel_count INTEGER NOT NULL,
    display_label TEXT NOT NULL,
    is_active BOOLEAN DEFAULT true NOT NULL,
    created_at TIMESTAMP WITH TIME ZONE DEFAULT timezone('utc'::text, now()) NOT NULL
);

-- 5. TRIPS TABLE (Core Fleet Lifecycle Records)
CREATE TABLE public.trips (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    vehicle_number TEXT NOT NULL,
    transporter_name TEXT NOT NULL,
    material_id BIGINT REFERENCES public.materials(id) ON DELETE RESTRICT,
    wheel_type_id BIGINT REFERENCES public.wheel_types(id) ON DELETE RESTRICT,
    status TEXT NOT NULL CHECK (status IN ('INSIDE_QUARRY', 'IN_TRANSIT', 'UNLOADED')),
    dispatch_location_id BIGINT REFERENCES public.locations(id) ON DELETE RESTRICT,
    unloading_location_id BIGINT REFERENCES public.locations(id) ON DELETE RESTRICT,
    gross_weight NUMERIC,
    tare_weight NUMERIC NOT NULL,
    net_weight NUMERIC,
    entry_photo_url TEXT,
    exit_photo_url TEXT,
    unload_photo_url TEXT,
    quarry_gps_lat NUMERIC(10, 8),
    quarry_gps_long NUMERIC(11, 8),
    is_flagged BOOLEAN DEFAULT false NOT NULL,
    check_in_time TIMESTAMP WITH TIME ZONE NOT NULL,
    check_out_time TIMESTAMP WITH TIME ZONE,
    unload_entry_time TIMESTAMP WITH TIME ZONE,
    unload_exit_time TIMESTAMP WITH TIME ZONE,
    created_at TIMESTAMP WITH TIME ZONE DEFAULT timezone('utc'::text, now()) NOT NULL
);

-- INDEXES FOR PERFORMANCE OPTIMIZATION
CREATE INDEX idx_trips_status ON public.trips(status);
CREATE INDEX idx_trips_vehicle_number ON public.trips(vehicle_number);
CREATE INDEX idx_trips_dispatch_loc ON public.trips(dispatch_location_id);
```

## 4. Business Logic & Mathematical Formulas

### **1. Net Weight Calculation**
When a lorry checks out of the quarry (`POST /api/trips/:id/check-out`), net payload weight is automatically computed:
$$\text{net\_weight} = \text{gross\_weight} - \text{tare\_weight}$$

### **2. Geofence Distance Validation (Haversine Formula)**
During check-out dispatch, the server computes the distance in meters between the operator's current GPS position $(\text{lat}_1, \text{lon}_1)$ and the designated quarry node coordinates $(\text{lat}_2, \text{lon}_2)$ using the **Haversine Formula** (`src/utils/geo.ts`):

$$\Delta\phi = \frac{(\text{lat}_2 - \text{lat}_1) \cdot \pi}{180}, \quad \Delta\lambda = \frac{(\text{lon}_2 - \text{lon}_1) \cdot \pi}{180}$$

$$a = \sin^2\left(\frac{\Delta\phi}{2}\right) + \cos(\text{lat}_1 \cdot \frac{\pi}{180}) \cdot \cos(\text{lat}_2 \cdot \frac{\pi}{180}) \cdot \sin^2\left(\frac{\Delta\lambda}{2}\right)$$

$$c = 2 \cdot \text{atan2}\left(\sqrt{a}, \sqrt{1-a}\right)$$

$$d = R \cdot c \quad \text{where } R = 6,371,000 \text{ meters}$$

If $d > \text{allowed\_radius\_meters}$ (default: $100\text{m}$), `is_flagged` is set to `true` on the trip record and flagged warnings appear on the Live Ledger screen.

## 5. Security & Authentication Architecture

### **JWT Authentication Pipeline (`src/middleware/auth.ts`)**
1. **Header Parsing**: Requests must supply `Authorization: Bearer <token>`.
2. **Token Verification**: Server decodes the token using `process.env.SUPABASE_JWT_SECRET`.
3. **Role Enforcement (`authorizeRole`)**:
   ```typescript
   authorizeRole(['SUPER_ADMIN'])
   ```
   Ensures that restricted administrative routes (Master Config edits, user creation, user deletion) can only be accessed by authenticated users whose profile role is `'SUPER_ADMIN'`.

### **Admin User Creation Bypassing Email Confirmation (`src/routes/index.ts`)**
When a Super Admin creates a user in `UserManagementScreen`, the backend uses the Supabase **Service Role Client** (`supabase.auth.admin.createUser`):
```typescript
const { data: authData, error: authError } = await supabase.auth.admin.createUser({
  email: email.trim(),
  password: password,
  email_confirm: true, // Bypasses email confirmation link requirement
  user_metadata: { full_name, role },
  app_metadata: { role },
});
```
If profile creation succeeds, it inserts into `public.profiles`. If the profile insert fails, it immediately triggers an atomic rollback by deleting the auth account (`supabase.auth.admin.deleteUser`).

## 6. Detailed API Route Specifications

### **Auth & User Routes**
| Method | Endpoint | Authorization | Description |
| :--- | :--- | :--- | :--- |
| `POST` | `/api/auth/login` | Public | Authenticates credentials and returns JWT session token. |
| `GET` | `/api/users` | `SUPER_ADMIN` | Returns list of all user profiles in `public.profiles`. |
| `POST` | `/api/users` | `SUPER_ADMIN` | Creates user account via Service Role client (bypasses email confirmation). |
| `DELETE` | `/api/users/:id` | `SUPER_ADMIN` | Removes user account from `auth.users` and `public.profiles`. |

### **Fleet Trips Routes (`/api/trips`)**
| Method | Endpoint | Authorization | Description |
| :--- | :--- | :--- | :--- |
| `GET` | `/api/trips` | Authenticated | Query trips. Accepts `?status=INSIDE_QUARRY\|IN_TRANSIT\|UNLOADED`. |
| `POST` | `/api/trips/check-in` | `QUARRY_OPERATOR` / `SUPER_ADMIN` | Creates trip entry with `INSIDE_QUARRY` status, vehicle #, wheel type, tare weight, entry photo. |
| `POST` | `/api/trips/:id/check-out` | `QUARRY_OPERATOR` / `SUPER_ADMIN` | Updates trip to `IN_TRANSIT`, computes net weight, validates GPS geofence. |
| `POST` | `/api/trips/:id/unload` | `UNLOAD_OPERATOR` / `SUPER_ADMIN` | Closes trip to `UNLOADED`, captures unloading location, unload entry/exit timestamps & photo. |

### **Master Configuration Routes (`/api/config`)**
| Method | Endpoint | Authorization | Description |
| :--- | :--- | :--- | :--- |
| `GET` | `/api/config/locations` | Authenticated | Retrieves locations list (optional `?type=QUARRY` or `?type=UNLOAD_SITE`). |
| `POST` | `/api/config/locations` | `SUPER_ADMIN` | Creates new location node. |
| `PUT` | `/api/config/locations/:id` | `SUPER_ADMIN` | Updates location name, coordinates, type, or radius. |
| `DELETE` | `/api/config/locations/:id` | `SUPER_ADMIN` | Deletes location (Guarded: returns HTTP 409 Conflict if mapped to trips). |
| `GET` | `/api/config/materials` | Authenticated | Retrieves active material types. |
| `POST` | `/api/config/materials` | `SUPER_ADMIN` | Appends new material type. |
| `PUT` | `/api/config/materials/:id` | `SUPER_ADMIN` | Updates material display name. |
| `DELETE` | `/api/config/materials/:id` | `SUPER_ADMIN` | Deletes material (Guarded: returns HTTP 409 Conflict if mapped to trips). |
| `GET` | `/api/config/wheel-types` | Authenticated | Retrieves wheel axle configurations. |
| `POST` | `/api/config/wheel-types` | `SUPER_ADMIN` | Appends lorry class configuration. |
| `PUT` | `/api/config/wheel-types/:id` | `SUPER_ADMIN` | Updates wheel class count/label or toggles active status. |
| `DELETE` | `/api/config/wheel-types/:id` | `SUPER_ADMIN` | Deletes wheel class (Guarded: returns HTTP 409 Conflict if mapped to trips). |

## 7. Client State Architecture & Performance Rules

### **1. In-Memory Config Caching & Zero-GET Updates (`AuthContext.tsx`)**
To minimize server roundtrips and avoid firing 3 GET network calls on every screen mount, `AuthContext` caches `materials`, `wheelTypes`, and `locations` in React memory.

Mutations call dedicated in-memory state updaters:
```typescript
addLocationState(res.data?.location || res.data);
updateLocationState(selectedLocId, res.data?.location || res.data);
removeLocationState(loc.id);
```
This strategy ensures **instant UI updates with ZERO follow-up GET requests**.

### **2. Modal Layout Rule (Preventing Height Collapse)**
In centered dynamic-height modals (`maxHeight: '85%'` or `'90%'`), avoid using `<ScrollView style={{ flex: 1 }}>` as it causes height collapse to 0 on React Native.
**Rule**: Always use `<ScrollView style={{ flexGrow: 0, flexShrink: 1 }}>`.

### **3. Soft Keyboard Form Layout Rule**
To ensure form input fields remain fully accessible above the soft keyboard:
- Wrap screen forms with `<KeyboardAvoidingView behavior={Platform.OS === 'ios' ? 'padding' : 'height'}>`.
- Set `contentContainerStyle={{ paddingBottom: 260 }}` on scroll content and pass `keyboardShouldPersistTaps="handled"`.

## 8. Development Setup & Execution Commands

### **Server Environment (`SM-Server`)**
1. Copy `.env` file to `SM-Server/.env`:
   ```env
   PORT=3000
   SUPABASE_URL=https://your-project.supabase.co
   SUPABASE_ANON_KEY=your-anon-key
   SUPABASE_SERVICE_ROLE_KEY=your-service-role-key
   SUPABASE_JWT_SECRET=your-jwt-secret
   ```
2. Start Development Server:
   ```bash
   cd SM-Server
   npm run dev
   ```
3. Compile Production Dist & Start Production Server:
   ```bash
   npm run build   # rimraf dist && tsc
   npm run start   # node dist/server.js
   ```

### **Client Environment (`SM-Client`)**
1. Configure `SM-Client/.env`:
   ```env
   EXPO_PUBLIC_API_URL=http://<YOUR_LOCAL_IP>:3000
   ```
2. Start Expo Bundler:
   ```bash
   cd SM-Client
   npm run start
   ```
